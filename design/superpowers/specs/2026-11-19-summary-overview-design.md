# 요약 보강 — 본문을 간추린 요약 하나로

2026-11-19. 사용자: "요약이 너무 대강이라 흐름을 파악하기 쉽지 않다."

## 진단 (2026-11-19 실제 브리핑 7건)

- 요약 1건 = 요점 3개(평균 81자) + "왜 중요한가" 1문장 ≈ **315자**.
- 요점이 **사실·수치의 나열**이다. 배경 → 무엇을·어떻게 → 결과가 문장 사이에서
  이어지지 않는다. 1번("코드 44%↑ / 이슈 13.7%↑ / PR 병합 56%↑")이 대표적이다.
- 원문 6,944~8,000자를 읽고도 315자만 쓴다. 프롬프트가 "요점 2~3개, 각 한
  문장"으로 묶었기 때문이다.
- GeekNews 글은 원문이 피드 발췌 316~370자라 이미 원문 길이만큼 요약하고 있다.
  보강할 재료가 없다.

## 결정

처음엔 "해설 문단 3~4문장 + 요점"을 제안했다. 사용자: **문단과 요점의 요지가
겹친다. 본문을 간추린 요약 하나로, 그리고 3~4문장으로는 부족하다.**

| 칸 | 전 | 후 |
|---|---|---|
| 헤드라인 | 30자 | 그대로 (카톡도 그대로 — 헤드라인 5개) |
| **본문 요약** `overview` | 없음 | 원문을 간추린 글. **2~3문단**, 문단마다 흐름의 한 단계 — ① 배경·문제 ② 무엇을·어떻게 ③ 결과·시사점. 문단은 빈 줄로 나눈다 |
| 요점 `bullets` | 2~3개 | **없앤다.** 새 요약은 빈 목록. 예전 글은 요점 그대로 보인다 |
| 왜 중요한가 | 1문장 | 그대로 — 내용의 반복이 아니라 "나에게 어떤 의미인가"라는 해석이다 |

### 길이는 원문에 비례한다

- 원문이 넉넉한 글(본문 확보, 수천 자): **약 700~1,000자** — 지금의 2~3배.
- 발췌로만 받은 글(`body_source = rss_excerpt`): **원문 길이를 넘지 않게.**
  짧은 원문을 "길게 써라"고 하면 모델이 지어낸다. 프롬프트의 글 머리에
  "(발췌 — 원문이 짧다)"를 붙여 모델이 알게 한다.
- 수치·고유명사·버전은 원문 그대로. **원문에 없는 내용은 쓰지 않는다.**

### 형식 실패로 7건을 잃지 않는다

2026-11-18에 헤드라인 `maxLength: 30` 위반 하나로 `SummarySheet` 전체가 거부돼
7건이 날아갔다. 같은 위험이 요점의 `max_length=3`에도 있었다(4개면 전체 거부).
원칙대로 **LLM 초안은 느슨하게, 우리 계약은 엄격하게, 경계에서 정규화**한다.

- `SummaryDraft.overview: str` — 길이 제약 없음.
- 빈 `overview`는 그 한 건만 버린다(시트 전체가 아니라).
- `Summary.overview: str | None` — 예전 `briefing.json`과 DB 행은 None이다.
- `Summary.bullets`는 기본값 빈 목록으로 남긴다 — 예전 데이터를 읽어야 한다.

## 바뀌는 곳

| 층 | 변경 |
|---|---|
| `pipeline/models.py` | `SummaryDraft`: `bullets` → `overview`. `Summary`: `overview` 추가, `bullets` 기본 빈 목록 |
| `pipeline/summarize.py` | 프롬프트 규칙, 발췌 표시, 빈 overview 거르기, 출력 예산 1건 400 → 1,300토큰 |
| `pipeline/lib/store.py` | `article_rows`에 `overview` |
| `supabase/` | `articles.overview text` (nullable), anon·authenticated에 SELECT(overview) — 컬럼 단위 grant라 자동으로 열리지 않는다 |
| `pipeline/lib/sender.py` | ConsoleSender가 본문 요약을 찍는다(로컬 튜닝용) |
| `web/` | Card가 문단을 나눠 그린다. overview가 없으면(예전 글) 요점을 그린다 |
| 카톡 | 변경 없음 |

## 비용

출력이 1회 약 5천 토큰 늘어 **+$0.10**. 1회 약 $0.42~0.66, 평일 월 약 $10~15.
예산 $30 안이다.

## 검증

- 단위 테스트: 초안 스키마, 프롬프트 규칙·발췌 표시, 빈 overview 한 건만 버리기,
  `article_rows`, 예전 데이터(bullets만 있음) 읽기.
- **같은 입력으로 전후 비교**: 2026-11-19 7건의 원문(`article_bodies`)으로
  ArticlesBundle을 다시 만들어 요약 단계만 실제 API로 돌린다(약 $0.3). 카톡·DB에는
  쓰지 않는다. 그날 나간 요약과 나란히 놓고 길이·흐름·지어내기 여부를 본다.
- 페이지: 새 글(문단)과 예전 글(요점) 둘 다 로컬 브라우저로 본다.

## 검증 결과 (2026-11-19)

**같은 입력으로 전후 비교.** 그날 7건의 원문(`article_bodies`)으로 요약 단계만
실제 API로 다시 돌렸다. 카톡·DB에는 쓰지 않았다. 58초, 입력 14,008 · 출력 5,104
토큰, 정가 $0.16(입력이 10건이 아니라 7건이라 적다).

| 글 | 원문 | 전 | 후 |
|---|---|---|---|
| GeekNews 3건 (발췌) | 316~370자 | 196~268자 | **234~320자**, 2문단 — 원문보다 짧다 |
| 본문 있는 4건 | 6,944~8,000자 | 215~305자 | **624~945자**, 3문단 |

**지어내기 없음.** GeekNews 1번의 새 요약을 원문 316자와 대조했다 — 모든 수치와
문장이 원문에 있다. 그러면서 "~늘었지만 ~에 그쳤고", "반면 PR 병합 시간은…"처럼
문장이 이어진다. AWS 3번은 원문 앞부분 밖의 수치(1.35배·2.5배·5회·`active=true`를
마지막에 쓴다)까지 원문에서 찾아 확인했다.

**흐름.** AWS 3번의 세 문단이 ① 왜 이 실험이 필요한가 ② 어떻게(로딩·SSM 제어·장애
두 종류·주의) ③ 실험 결과와 한계를 맡는다. 전에는 같은 글이 사실 세 줄이었다.

**페이지.** 예전 글(overview 없음) 7건이 요점으로 그대로 그려진다(회귀 없음).
`articles?select=…overview…`가 anon으로 200이다. 새 형식은 다음 실행(11/20)부터 보인다.
콘솔의 401은 로그인 전 `reactions` 조회로, 계획 2부터 있던 것이다.

## 후속: 잘린 원문 끝에서 지어냈다 (2026-11-20)

새 형식의 첫 실행(11/20). 7건 모두 문단으로 나갔고 페이지에 정상 표시됐다.
본문 있는 글은 776·1,331자. 정가 $0.34.

**5번(GeekNews, 원문 313자)이 "smoltcp, DPDK, AF_XDP를 이용해"라고 썼다.** 원문은
`…메모리 병목으로 남음 smo …`에서 잘려 끝난다. DPDK·AF_XDP는 원문에 없다 — 모델이
잘린 "smo"를 보고 배경지식으로 채웠다. "원문에 없는 내용 금지" 규칙이 잘린 끝에서
깨졌다.

잘린 끝은 두 모양이었다(`article_bodies` 28행 전수).

- GeekNews 발췌: `…`로 끝나고 앞 단어가 잘릴 수 있다 — `smo …`, **`Ruby 3.3.14, 3.4.13, 4. …`**
  (버전 번호가 잘리면 모델이 버전을 지어낸다).
- enrich의 8,000자 자르기: 단어 중간에서 **표시 없이** 끊긴다 — `wou`, `virt`, `predicti`.

**고친 것 — 두 겹.** 저장된 원문은 건드리지 않고 모델에게 보낼 때만 다듬는다.

1. `summarize.prepare_body`: 발췌가 `…`로 끝나면 줄임표와 그 앞의 잘린 영문·숫자 조각을
   뗀다(한국어 단어는 남긴다 — 메모체 발췌는 마지막 단어가 대개 완결돼 있다). 8,000자에서
   잘린 본문은 마지막 완결 문장까지 되돌린다. 둘 다 `[원문이 여기서 끊겼다]`를 붙인다.
2. 프롬프트: 도구·제품·라이브러리 이름과 버전·수치는 **원문에 철자 그대로 있는 것만**,
   잘린 단어를 추측해 완성하지 않는다.

**점검 — `summarize.unsupported_terms`.** 요약에 나오지만 원문(제목·출처·본문)에 없는 영문
용어를 실행 로그에 찍는다. 막지는 않는다 — 단서다. 처음 버전은 오탐이 둘이었다: 출처 이름
(`Simon Willison`, 프롬프트의 출처 줄에서 봤다)과 복수형(`canaries` → `canary`). 대조 범위에
제목·출처를 넣고 끝 글자 하나 차이는 통과시켰다. DPDK·AF_XDP는 여전히 잡힌다.

**재확인** (같은 7건, 실제 API, 카톡·DB에 쓰지 않음, 정가 $0.14): 5번의 지어낸 이름이
사라졌고 요약이 원문의 마지막 사실에서 끝난다. 발췌 글은 원문 대비 +7~14자(메모체를
완결 문장으로 바꾼 만큼). 점검에 남은 2번 `Radim Marek`은 원래 제목("Radim Marek: Your
biggest tenant…")에 있다 — 지어낸 것이 아니다.

## 후속: 발췌 후보는 하루 2건까지 (2026-11-23)

새 형식이 운영에서 동작했다 — 11/23 본문 있는 글 4건이 488~1,033자, 용어 점검 경고 0건.
그런데 GeekNews 글은 글 페이지가 403이라 늘 300자대 발췌로만 요약된다. 최종 7건 중
11/19 3건, 11/20 5건(GeekNews 4 + Lobsters 1), 11/23 3건이 발췌 기반이었다. 요약을
보강해도 하루의 절반 가까이는 혜택을 못 받는다. 가중치 1.2 → 1.0(11/19)은 효과가 거의
없었다 — 원래 점수가 높다.

**사용자 결정: 발췌 기반 후보는 하루 2건까지.** 점수가 높은 발췌 2건은 남는다.

**어디서 거르나.** 요약 뒤에 거르면 모델이 이미 7건만 골라 둔 상태라 빈자리가 생긴다
(6건). 요약 앞, 후보 단계에서 거른다. 그런데 후보 10건 중 발췌가 날마다 크게 달랐다 —
11/19 4건, **11/20 6건**, 11/23 3건. 빼기만 하면 11/20은 후보가 6건으로 줄어 7건을 못
채운다.

**그래서 예비 후보.** rank가 본문을 가져올 후보를 10 → **14건**(요약 후보 10 + 예비 4)으로
넘기고, enrich가 점수 순서대로 가져오며 발췌는 2건까지만 받고 후보가 10건 차면 멈춘다.

- 요약 후보는 그대로 10건 — 요약 입력 토큰과 비용이 같다.
- 발췌가 2건 이하인 날은 예비를 요청하지 않는다 — 요청 수가 전과 같다.
- 발췌가 많은 날은 원문 요청이 최대 4건(약 6~10초) 는다.
- 예비까지 다 써도 모자라면 있는 만큼만 넘긴다 — 지어서 채우지 않는다.

확인은 다음 실행 로그의 `[발췌]` 수(2 이하)로 한다.
