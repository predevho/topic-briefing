## 기준선 0.52 — 실측 (기존 35건, 2026-11-23)

과거 날짜 쌍 490개 중 0.50 이상 21개, 0.52 이상 13개. 가장 비슷한 과거 글의 유사도는
최고 0.655, 중간 0.490.

- 0.52 이상은 대부분 실제로 이어지는 주제였다 — 에이전트 샌드박스 ↔ 망분리 Agent Platform
  (0.655), 장애 주입 ↔ Durable Execution(0.575), Postgres generic plan ↔ 임시 테이블(0.570),
  Ruby·Rails RCE ↔ NGINX RCE(0.566), S3 형식검증 ↔ 결정론적 시뮬레이션(0.520).
  어색한 것은 Rust 이식 도구 ↔ Gemini 느린 이유(0.544) 하나.
- 0.50~0.52는 "둘 다 AI·서버 이야기" 수준으로 느슨하다 — 웹 서버 1,500만 개 ↔ SSE 기상악화
  알림(0.505). 지금 모이는 글이 AI 에이전트 쪽에 몰려 그 정도 공통점만으로 0.5 근처가 나온다.
- 0.55로 올리면 7쌍만 남고 Netflix ↔ Netflix(0.549) 같은 좋은 짝이 빠진다. 링크만 보여 주는
  단계라 하나쯤 어긋나도 피해가 작아 0.52를 골랐다(사용자 결정).

글이 다양해지면 분포가 바뀐다. 한 달쯤 뒤 다시 잰다.

## 고르지 않은 대안 (나중의 전체 점검을 위해)

**임베딩을 로컬 모델로** (`sentence-transformers` + multilingual-e5·bge-m3 같은 공개 모델).
계정·키·요청 한도·외부 의존이 없고 무료다. 대신 매일 실행에 PyTorch 같은 큰 의존성과 모델
파일(수백 MB~2GB)이 붙어, 캐시를 써도 첫 실행·캐시 만료 때 몇 분씩 늘어난다. 하루 7건,
300토큰짜리 글이라 성능은 어느 쪽이든 충분하다 — 차이는 "외부 계정 하나" vs "매일 실행이
무거워짐"이다. Voyage를 고른 이유: Anthropic은 자체 임베딩 모델이 없고 공식 문서가 Voyage를
소개한다, 다국어 최적화, 처음 2억 토큰 무료(우리는 연 약 100만), 실행이 HTTP 한 번이라 가볍다.

**MongoDB는 데이터베이스로 쓰지 않는다.** Voyage AI가 MongoDB에 인수돼 API 키를 MongoDB
Atlas에서 발급할 뿐이다. 벡터는 우리 Supabase에 저장된다.

**유사도 계산을 Python에서.** 실험(35건)은 실제로 Python에서 벡터 내적으로 계산했다. 수천
건이어도 충분히 빠르다. DB(pgvector)에서 하는 이유는 매일 모든 벡터를 내려받지 않아도 되고,
나중에 검색창·챗봇처럼 페이지에서 그때그때 찾는 기능이 같은 저장소를 쓰기 때문이다.

## 보안

- `article_embeddings`: RLS 켜고 anon·authenticated 권한 없음. 페이지에 필요 없다.
- `article_links`: id와 유사도뿐이라 공개 읽기. 페이지는 관련 글의 날짜·헤드라인을 FK로
  `articles`에서 읽는다(이미 공개 컬럼).
- 연결 함수 `link_related`: Postgres는 새 함수에 EXECUTE를 PUBLIC으로 준다 — anon·authenticated·
  PUBLIC에서 회수하고 service_role만 부른다.
- 원문 본문(`article_bodies`)은 임베딩에 쓰지 않는다 — 공개 요약만 쓴다.
- `article_links` 쓰기 권한: Supabase 기본 권한이 anon·authenticated에 insert·update·delete를 준다.
  select 정책만 있어 RLS가 막지만, 권한 자체를 회수했다(정책 실수 하나로 열리지 않게).
  `scripts/verify_anon_access.sh` 7번 항목이 링크 읽기·벡터 차단·링크 삽입 차단·함수 호출 차단을 점검한다.
