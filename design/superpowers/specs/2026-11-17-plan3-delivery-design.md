# 계획 3 설계 — 전달과 자동화

**범위:** `KakaoSender`, `SlackSender`, `lib/kakao`(토큰 갱신), `lib/guard`(경고 장치), GitHub Actions 워크플로, 실패 리포트.

**이 문서의 위치:** 기존 설계 스펙(`2026-11-10-it-column-automation-design.md`)의 6.1~6.3과 8.4~8.6을 **대체하지 않는다.** 그 절들의 판단 중 유효한 것(카카오 200자 계산, 슬랙을 경고 전용으로 둔 이유, `Sender` 프로토콜, 가드의 가치 순서)은 그대로 쓰고, **측정해 보니 성립하지 않은 전제 세 가지를 고친다.**

---

## 0. 이 설계가 고치는 것

세 가지가 전부 같은 모양이었다 — **문서에 적어 둔 전제가 실제로는 없었다.**

| 스펙이 적은 것 | 실제 | 고친 방향 |
|---|---|---|
| 8.4 "월 크레딧의 **일정 비율** 초과" | Anthropic API에 **잔액 엔드포인트가 없다.** Usage and Cost Analytics는 "얼마 썼나"만 준다 | 우리 사용량을 누적해 **내가 정한 예산**과 비교한다 |
| 8.4 소스 침묵 "3일 연속 0건" | 가동 45개 중 **30개 가까이가 오탐.** 느린 다섯 개만의 문제가 아니었다 | 지표를 바꾸고 등급 넷으로 묶는다. 느린 소스는 **가드에서 뺀다** |
| 8.6 워크플로 재시도 | 수집 윈도우가 이미 흡수한다 | **재시도하지 않는다** |

### 0.1 크레딧 — 잔액을 알 방법이 없다

Anthropic의 Usage and Cost Analytics API(`/v1/organizations/analytics/{usage,cost}`)를 확인했다.

- `/cost`의 `amount`는 **"할인 후, 크레딧 적용 전"** 금액이다. 쓴 돈이지 남은 돈이 아니다
- **Admin API 키**(`sk-ant-admin...`) 또는 `org:admin` OAuth 토큰이 필요하다. 일반 `ANTHROPIC_API_KEY`는 거부된다
- 데이터가 **4~24시간** 지연된다

즉 "월 크레딧의 일정 비율"의 **분모를 구할 수 없다.** 그리고 분모를 안다 해도, 조직 관리 권한을 들고 다니는 키를 매일 도는 자동화에 넣는 것은 가드 하나치고 폭발 반경이 크다.

**그래서 우리 사용량을 누적한다.** 두 번째 발동 조건("입력 토큰이 평소의 3배")은 어차피 우리 이력으로만 판정되므로, Admin API를 붙여도 그쪽은 못 쓴다. 대가는 근사치라는 것이다 — 할인과 크레딧 적용 전의 정가 기준이 된다.

### 0.2 소스 침묵 — 측정이 전제를 뒤집었다

시드(400일 윈도우, 1,923건, 45개 소스)로 소스별 발행 간격을 쟀다.

**중앙 간격으로 본 분포:**

| 중앙 간격 | 소스 수 | "3일 연속 0건"이면 |
|---|---|---|
| 0~1일 | 15 | 정상 동작 |
| 2~8일 | 9 | 매주 오탐 |
| 10~28일 | 7 | 상시 오탐 |
| 54~166일 | 2 | 영구 오탐 |

**그리고 중앙값으로는 임계값을 정할 수 없다.** 몰아서 쓰는 소스가 있다.

```
뱅크샐러드_기술블로그   중앙  2일   최대공백 265일
Discord_Engineering    중앙  4일   최대공백  52일
쏘카_기술블로그        중앙 11일   최대공백 119일
```

임계값이 넘어야 하는 것은 **관측된 최대공백**이다.

### 0.3 Actions 재시도 — 설계가 이미 흡수한다

수집 윈도우가 "마지막 발송 이후"(최대 96시간)다. 오늘 실패하면 `runs`에 `sent`가 남지 않고 **다음 날 실행이 이틀치를 덮는다.** 계획 1이 주말·공휴일·장애 복구를 한 규칙으로 처리하려고 그렇게 설계했고, 여기서 값을 한다.

| 실패 종류 | 이미 있는 처리 |
|---|---|
| 일시적 (네트워크·429) | `lib/http`의 `Transient` 재시도 + anthropic SDK `max_retries` |
| 영구적 (키 만료·설정 오류) | 재시도해도 같은 결과. **경고가 필요하다** |
| 부분 (발송 후 저장 실패) | `runs.errors`에 기록, 실행은 `sent` |

워크플로 수준에서 더할 것이 없다. 필요한 것은 재시도가 아니라 **실패가 나에게 닿는 것**이다.

## 2. KakaoSender

상위 5건 + "외 N건", 버튼이 `PAGE_URL`로. 조립 결과가 200자를 넘으면 **뒤쪽부터 접어** 반드시 제약 안에 맞춘다.

```
📡 11/17 IT 브리핑 · 7건

1. (헤드라인)
2. (헤드라인)
3. (헤드라인)
4. (헤드라인)
5. (헤드라인)
   외 2건

[전체 보기]  ← PAGE_URL
```

**검증 항목: 두 링크 모두 도달 확인.** 2026-11-17에 두 번 막히고 배웠다 — 카카오 메시지에는 링크가 둘이고 성격이 다르다.

| 링크 | 목적지를 정하는 것 |
|---|---|
| [전체 보기] 버튼 | 템플릿의 `link.web_url` |
| 하단 앱 바로가기 | **콘솔의 등록 도메인** — 코드로 못 건드린다 |

둘 다 `result_code: 0`으로는 검증되지 않는다. 메시지는 정상 접수되고 폰에도 도착한다. 자세한 것은 기존 스펙 6.1에 적었다.

## 3. SlackSender — 경고 전용

**브리핑 전문을 보내지 않는다**(스펙 6.2). 읽는 자리는 페이지이고, 채널이 둘이면 포맷터를 둘 유지해야 한다. 가는 것은 셋이다.

1. `collect_warnings`의 결과 — 발췌 폴백, 고쳐야 할 소스, 주소가 이전된 소스
2. `lib/guard`의 경고 — 침묵·토큰 만료·크레딧
3. 단계 실패 리포트 — 어느 단계에서 왜 죽었는지

슬랙이 필요한 이유는 하나다 — **카카오 토큰이 만료되면 카톡으로는 그 사실을 알릴 수 없다.** 슬랙 Incoming Webhook은 만료가 없다.

## 4. lib/guard

가치 순서는 **소스 침묵 > 토큰 만료 > 크레딧**이다(스펙 8.4). 토큰 만료는 겪으면 알게 되고 복구된다. **소스 침묵은 겪어도 알 수 없다** — 브리핑은 정상적으로 오고 내용만 조금씩 빈약해진다.

### 4.1 소스 침묵

**지표를 바꾼다.** "N일 연속 0건"이 아니라 **"그 소스에서 마지막으로 글이 온 날로부터 경과일"**이다.

"0건"은 수집 윈도우(최대 96시간) 기준이라 주간 소스는 7일 중 5일이 0건이고, "연속" 카운트가 소스의 실제 상태와 어긋난다. 경과일은 직접적이고, **이미 저장된 `runs.source_counts`를 거슬러 올라가면 유도된다** — 새 컬럼이 필요 없다.

```python
def quiet_days(runs: list[Run], source: str) -> int | None:
    """그 소스에서 마지막으로 글이 온 실행 이후 며칠인가.

    runs는 briefing_date 내림차순. 한 번도 못 봤으면 None이다 —
    "오래 조용하다"와 "처음부터 없었다"는 다른 문제다.
    """
```

**임계값은 등급 넷으로 묶는다.** 45개에 숫자를 손으로 적지 않고, 새 소스를 넣을 때도 등급만 고른다. 등급은 **관측된 최대공백**으로 나눈다.

| 등급 | 최대공백 | `quiet_days` |
|---|---|---|
| `fast` | ≤ 16일 | **30** |
| `weekly` | 17~45일 | **90** |
| `monthly` | 46~130일 | **200** |
| `none` | 131일+ 또는 표본 3건 미만 | **가드 제외** |

`sources.yaml`의 `Source` 모델에 `quiet_tier` 필드를 더한다(기본 `fast`).

괄호는 관측된 최대공백.

> **이 가드는 빠른 25개에만 의미가 있다 — 그렇게 설계했다.** 느린 소스는 침묵이 정보를 담지 않는다. 400일에 2편인 Lil'Log를 400일 기준으로 감시하는 것은 가드가 아니라 가드인 척이고, 그 한 줄이 "우리는 이 소스를 감시하고 있다"는 **잘못된 안심**을 준다. 숫자를 억지로 주는 대신 명시적으로 뺀다.
>
> **제외한 소스는 분기에 한 번 `check_feeds.py`로 확인한다.** 그 스크립트가 구조적 고장(404·403·0건·내용 불일치)을 잡는다. 자동 가드가 못 잡는 것은 "피드는 멀쩡한데 블로그가 멈췄다"뿐이고, 그건 느린 소스에서는 1년이 지나야 판정된다.

**피드 잘림 주의.** 시드의 건수가 10·20·50·100처럼 딱 떨어지는 소스는 피드가 잘린 것이고, 관측 최대공백이 **과소평가**돼 있다. 등급이 한 칸 낮게 잡혔을 수 있으므로, 오탐이 나면 그 소스를 한 등급 올린다.

### 4.2 토큰 만료

`kakao_auth.refresh_token_expires_at`이 **14일 안**이면 슬랙 경고 + 재인증 방법 안내.

2026-11-17 실측: 발급된 `refresh_token`의 수명은 **60일**이었다. 수명을 하드코딩하지 않고 `refresh_token_expires_in`을 저장해 쓰기로 한 스펙 6.3의 판단이 맞았다. 그리고 새 `refresh_token`은 기존 만료가 1개월 미만일 때만 응답에 오므로, 매일 돌아도 저장소 쓰기는 **한 달에 한 번**이다.

### 4.3 크레딧

**선행 작업: `runs.input_tokens`·`output_tokens` 배선.** `AnthropicLLM.parse`가 토큰 수를 돌려주는데 `rank`와 `summarize`가 그 값을 버린다. `RankedBundle`과 `Briefing`에 실어 `notify`까지 보낸다. `input_tokens` 컬럼은 이미 있고, `output_tokens`는 더한다.

> **새 컬럼에 anon 권한을 주지 않는다.** `runs`는 컬럼 단위 grant이고 `input_tokens`가 의도적으로 빠져 있다(계획 2 마이그레이션). `output_tokens`도 같은 이유로 준다. 컬럼을 더할 때 grant 목록을 손대지 않으면 자동으로 막히지만, `scripts/verify_anon_access.sh`의 컬럼 차단 검사에 한 줄 더해 실측으로 확인한다.

| 발동 조건 | 판정 |
|---|---|
| 월 누적 비용이 예산의 **80%** 초과 | `runs`의 당월 토큰 × 가격표 vs `.env`의 `MONTHLY_BUDGET_USD` |
| 오늘 입력 토큰이 **평소의 3배** 초과 | 최근 14일 중앙값과 비교 |

두 번째가 더 값지다. 피드 하나가 갑자기 10배를 쏟아내는 것 같은 **당일 이상**을 잡는다. 첫 번째는 느린 누수를 잡는다.

가격표는 모델별 상수로 둔다(현재 `claude-opus-5-5`: 입력 $4 / 출력 $20 per MTok). **정가 기준이라 실제 청구액과 다르다** — 할인과 크레딧 적용 전이다. 이 가드의 목적은 정확한 금액이 아니라 **조기 소진 감지**다.

> **크레딧 가드의 의미는 요금 폭주 방지가 아니라 조기 소진 방지다**(스펙 8.4). Max 크레딧은 이월되지 않고, 월 중반에 바닥나면 그 달의 나머지 기간 브리핑이 오지 않는다.

### 4.4 알림 피로

임계값을 모두 느슨하게 둔 이유는 **알림 피로**다. 오탐이 세 번 나면 경고를 무시하게 되고, 그러면 경고 시스템이 있는 것이 없는 것보다 나쁘다.

같은 이유로 `collect_warnings`는 `transient`를 제외한다(계획 1). 내가 할 일이 없는 것은 알리지 않는다.

## 5. GitHub Actions

```yaml
on:
  schedule:
    - cron: '20 22 * * 0-4'   # UTC → 월~금 07:20 KST
  workflow_dispatch:

jobs:
  briefing:
    steps:
      - run: python -m pipeline.collect
      - run: python -m pipeline.rank
      - run: python -m pipeline.enrich
      - run: python -m pipeline.summarize
      - run: python -m pipeline.notify
      - if: failure()
        run: python -m pipeline.report_failure
```

**정각을 피한 이유**는 GitHub Actions cron이 정각에 전 세계 작업이 몰려 지연이 가장 크기 때문이다.

**넣지 않는 것:**

- **재시도** — 0.3 참조. 실패하면 알리고 끝낸다
- **`render` 단계** — 없어졌다. 페이지가 Supabase를 직접 조회한다
- **`prune.py`** — 러너의 `data/`는 잡과 함께 사라진다. 지울 것이 없다. 로컬 전용이다
- **Node 셋업** — 프론트엔드는 Vercel이 푸시를 받고 따로 빌드한다

`workflow_dispatch`를 두어 손으로 돌릴 수 있게 한다. 같은 날 다시 보내야 하면 `notify --force`를 쓴다.

## 6. 실패 알림 (`report_failure`)

1. GitHub Actions 실패 시 자동 메일 (기본 제공)
2. **슬랙에 실패 리포트** — 어느 단계에서 왜 죽었는지
3. 부분 실패도 리포트 — "7건 중 2건은 RSS 발췌로 폴백"

**메일은 크래시만 잡고, 성공적으로 끝나는 품질 저하는 못 잡는다.** "소스 하나가 석 달째 조용", "7건 중 5건이 발췌 폴백", "크레딧 80% 소진"은 실행이 정상 종료되므로 메일이 오지 않는다. 그것이 시스템을 서서히 망치는 종류의 실패다.

## 9. 의도적으로 하지 않는 것

- **Admin API로 실제 청구액 조회** — 0.1 참조. 잔액을 주지 않는데 조직 관리 권한 키와 4~24시간 지연이 따라온다
- **느린 소스의 침묵 감시** — 4.1 참조. 정보를 담지 않는 신호를 감시하는 척하지 않는다
- **워크플로 재시도** — 0.3 참조. 윈도우가 흡수한다
- **중간 산출물을 아티팩트로 보존** — 재실행 시 `rank`를 다시 내는 비용보다 워크플로 복잡도와 "낡은 산출물로 이어가다 조용히 틀리는" 위험이 크다
- **외부 사용자에게 알림** — 카카오 메시지 API는 같은 서비스 내 사용자 간 발송만 지원한다. 서비스→사용자 직접 발송은 사업자(채널·알림톡) 영역이다. 다수 사용자가 목표가 되면 슬랙·텔레그램·이메일로 간다 (설계 2.1)
- **사용자별 브리핑** — 설계 2.1: "비용이 아니라 근거가 없기 때문이다"
