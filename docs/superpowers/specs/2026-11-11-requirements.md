## 6. 빈칸 — 이 문서를 쓴 이유

### 6.1 ⚠️ C5 — 발송 요일에 검증 수단이 없다

**발견한 것이 이것 중 가장 실질적이다.**

스펙 7.4는 "KST 월~금은 UTC 일~목이므로 cron은 `20 22 * * 0-4`"라고 적었고, 계획 3에서 그 문자열을 워크플로에 넣는다. 그런데 **이것이 맞는지 확인하는 수단이 수동 관찰뿐이다.**

틀리기 쉬운 이유가 두 겹이다.

1. **UTC 22:20 + 9시간은 "익일" 07:20이다.** 그래서 KST 요일이 UTC 요일보다 하루 앞선다.
2. **cron의 요일 번호는 0 = 일요일인데, Python `datetime.weekday()`는 0 = 월요일이다.** 같은 숫자가 다른 요일을 뜻한다.

한 칸 밀리면 **토요일에 발송되고 월요일이 빠진다.** 월요일은 주말 해외 콘텐츠를 72시간 윈도우로 받는 날이므로, 하필 가장 중요한 날이 사라진다. 그리고 **증상이 "일주일에 한 번 이상한 날에 온다"라서 알아차리기까지 오래 걸린다.**

→ **조치 완료.** `lib/timeutil`에 `SEND_CRON_UTC`·`SEND_HOUR_UTC`·`SEND_MINUTE_UTC` 상수를 두고, 테스트 두 개를 붙였다.

- `test_발송_cron이_KST_월금에_해당한다` — cron `0-4`가 KST 월~금이 되는지 확인
- `test_cron_요일을_하나_밀면_월요일이_빠지고_토요일에_발송된다` — **무엇을 막는지** 보여준다. 한 칸 밀면 화~토가 되고 월요일이 사라진다

순수한 시각 계산이므로 계획 1에서 검증되고, 계획 3의 워크플로는 그 상수를 참조한다. 상태: ⚠️ → ✅

### 6.2 ⚠️ R10 — 계획 1의 비밀값 노출 경로가 점검되지 않았다

계획 3의 슬랙 웹훅은 테스트로 막았다(`test_에러_메시지에_웹훅_URL이_들어가지_않는다`). 그런데 **계획 1에도 비밀값이 있다 — `SUPABASE_SECRET_KEY`다.**

`SupabaseStore`가 실패할 때 `supabase-py`가 올리는 예외 메시지에 요청 헤더나 URL이 포함되는지 **확인하지 않았다.** 포함된다면 Actions 로그에 service_key가 남는다. 그건 리포지토리가 퍼블릭이라는 전제와 정면으로 충돌한다 — Actions 로그는 퍼블릭 리포에서 누구나 볼 수 있다.

→ **조치 완료.** `smoke_supabase.py`에 5단계를 넣었다. 실제 키 대신 센티넬 문장을 키 자리에 넣어 호출하고, 그 문장이 예외 메시지에 나타나는지 본다. 나타나면 실제 키도 같은 자리에 나타난다는 뜻이다.

실제 키를 쓰지 않으므로 이 점검 자체가 키를 노출하지 않는다. Task 22 완료 조건에 "5단계가 '키는 새지 않았다'로 끝난다"를 넣었다. 상태: ⚠️ → 🔍

### 6.3 ❓ 페이지 다크모드 색

목업에 다크 버전이 없다. 아침에 폰으로 보는 도구이므로 필요성이 높은데, **지금 정하지 않으면 계획 2 구현 중에 임의로 정해진다.**

→ **계획 2 시작 전에 결정한다.** 캔버스에 다크 아트보드 하나를 추가하는 것으로 끝난다.

### 6.4 ❓ `runs.input_tokens`가 항상 NULL이다

`lib/llm`은 입력 토큰 수를 돌려주지만 `rank`와 `summarize`가 버린다. 계획 3의 크레딧 가드(R11)가 이 값을 쓰므로 그때 배선한다 — 계획서에 구체적인 단계를 적어뒀다.

### 6.5 🔍 C8·S16 — 품질은 테스트하지 않는다 (의도)

"같은 사건 중복을 잘 걸러내는가", "요약이 읽을 만한가"는 단위 테스트의 대상이 아니다. 시도하면 깨지기만 하는 테스트가 된다.

→ **대신 `evaluate.py`와 Task 22 Step 3의 수동 확인이 그 자리를 맡는다.** 이것은 빈칸이 아니라 의도적 선택이므로, 나중에 "왜 테스트가 없나"라고 다시 묻지 않도록 여기 적어둔다.

### 6.6 다수 사용자 전환 — 문서화하고 미룸 (빈칸 아님)

"정보는 모두에게 공개, 알림은 로그인한 권한자에게"로 확장하는 경우를 **설계 스펙 2.1에 항목별로 정리했다.** 전환하지 않았지만 판단 근거는 남겼다.

그중 **하나만 지금 했다** — 반응 테이블의 `user_id`(D13·D14). 나머지는 나중에 해도 같은 가격이거나, 지금 할 수 없는 것이다(카카오의 서비스→사용자 알림은 비즈니스 영역, 큐레이션 모델은 실제 사용자 반응을 봐야 정함).

이것을 빈칸으로 세지 않는 이유: **요구사항이 아니라 미래의 선택지**다. 지금 충족해야 할 것이 아니다. 다만 "나중에 생각하자"로 흘리면 그때 처음부터 다시 조사하게 되므로 적어뒀다.

### 6.7 Phase 3 미결 (ERD 6장과 동일)

임베딩 차원 `vector(N)`과 pgvector 인덱스 종류. 모델 선택 후 결정한다.

### 6.8 ⚠️ R2의 빈 구석 — DB 계층 예외가 분류되지 않는다 (알려진 한계로 수용)

6.2를 점검하다 발견했다. R2를 ✅로 적었는데 **그것은 HTTP(`lib/http`)와 LLM(`lib/llm`)에만 해당한다.** `SupabaseStore`는 `supabase-py`의 예외를 그대로 올린다. 그래서 **Supabase의 일시 장애(503)와 잘못된 키(401)가 구분되지 않는다.**

실제 영향: 수집 단계의 `remote.last_sent_at()`에서 Supabase가 일시적으로 죽으면, 분류되지 않은 예외로 파이프라인이 중단된다. 재시도가 걸리지 않는다.

**그런데 이것을 지금 고치지 않는다.** 이유는 두 가지다.

1. **스스로 복구된다.** 그날 실패하면 `runs`에 아무 기록도 남지 않고, 다음날 `compute_window`가 "마지막 발송 이후"로 윈도우를 넓혀 그 사이 글을 다 가져온다. 하루 늦게 오지만 글이 유실되지는 않는다.
2. **고치는 비용이 작지 않다.** `SupabaseStore`의 다섯 메서드를 전부 감싸고 PostgREST의 에러 코드를 Transient/Permanent로 매핑해야 한다. 1인용 도구에서 Supabase 장애 빈도를 생각하면 지금 할 일은 아니다.

→ **알려진 한계로 수용한다.** 실제로 이 경로에서 실패가 반복되면 그때 고친다. R2의 상태를 "✅ (HTTP·LLM) / ⚠️ (DB 계층, 수용)"으로 바꾼다.

이것을 적어두는 이유는, 나중에 "분류가 다 돼 있는 줄 알았는데"가 되지 않게 하는 것이다.
