# IT 토픽 자동 수집·요약·전송 시스템 설계

- 작성일: 2026-11-10
- 상태: 승인됨 (Phase 1 구현 대기)
- 데이터 모델: `2026-11-11-erd.md` (관계도, 공개 범위, Phase 3 임베딩 결정)
- 페이지 디자인: 캔버스 목업 — A 톤 확정

## 1. 목적

매일 아침, 내가 관심 있는 IT 토픽을 자동으로 수집·선별·요약해서 카카오톡으로 받는다. 전문은 공개 웹페이지에서 읽고, 날짜별로 영구 보관한다. 슬랙은 **운영 경고 전용 채널**로 둔다(6.2).

**사용자: 본인 1인.** 외부 구독자나 팀 공유는 범위 밖이다. 이 전제가 인증·심사·구독 관리를 전부 제거한다.

**관심 주제:** AI, 백엔드, 새로운 기술, AI를 활용한 스킬·사례. 이 네 축이 큐레이션 기준의 출발점이다.

**수집 대상 네 종류:**
- 국내 IT 매체의 컬럼·사설
- 기업·개발자의 기술 분석글 (기업 기술블로그 등)
- 해외 IT 뉴스레터·바이럴 콘텐츠
- 특정 주제 추적 (소스 무관, 주제 기준)

## 2. 범위 (Phase 구분)

| Phase | 내용 | 조건 |
|---|---|---|
| **Phase 1** | 파이프라인 6단계 + React 반응형 페이지 + 좋아요·클릭·메모 저장 + 본문 적재 | 지금 구현 |
| **Phase 2** | 좋아요·클릭을 선별 프롬프트에 주입 + 태그 필터 + 전진 검색 | 데이터 2주 축적 후 |
| **Phase 3** | 적재된 본문에 임베딩 → RAG 챗봇 | 데이터 충분히 축적 후 |

**Phase 1에서 좋아요·클릭을 저장하되 큐레이션에 쓰지 않는다.** 피드백 루프는 데이터가 2주쯤 쌓여야 효과가 나므로, 수집은 오늘부터 하고 활용은 나중에 한다. 이렇게 하면 Phase 2가 "프롬프트 수정 + 쿼리 하나"로 끝난다.

**Phase 3을 가능하게 하는 Phase 1의 필수 조건:** `articles.body`에 추출한 본문 전문을 처음부터 저장해야 한다. 과거 기사는 삭제되고 유료화되고 링크가 썩으므로, 나중에 다시 모을 수 없다. 임베딩·벡터 검색은 Phase 3에 해도 되지만 원문 적재는 1일차부터 해야 한다. 하루 10건 x 8,000자 약 80KB, 1년 약 30MB로 Supabase 무료 티어 안이다.

## 3. 아키텍처

```
┌─ GitHub Actions (월~금 07:20 KST) ──────────┐
│ collect → rank → enrich                     │
│ → summarize → render → notify               │
└──────┬──────────────┬───────────────┬───────┘
       │              │               │
  Supabase       docs/data/*.json   카카오톡 (+ 슬랙 경고)
 (토큰/본문/       → GitHub Pages
  좋아요/클릭)          ↑
       ↑                │
       └── 좋아요·클릭 ──┘
```

### 3.1 파이프라인 구조: 단계별 독립 실행 + 중간 JSON

각 단계가 `data/YYYY-MM-DD/` 안에 자기 결과를 JSON으로 떨어뜨리고, 다음 단계는 그 파일을 입력으로 읽는다.

```
collect.py    → raw.json        (수집 원본, 수십~수백 건)
rank.py       → ranked.json     (전체 점수 + 상위 10건)
enrich.py     → articles.json   (본문 확보한 10건)
summarize.py  → briefing.json   (임계값 통과분, 최대 7건)
render.py     → docs/data/YYYY-MM-DD.json
notify.py     → Sender 목록으로 전송 (카카오톡 / 슬랙 경고)
```

각 단계는 `python -m pipeline.collect`처럼 모듈로 실행한다. **숫자 접두 파일명(`01_collect.py`)을 쓰지 않는 이유는 Python에서 import가 불가능해 테스트를 쓸 수 없기 때문이다** (`import 01_collect`는 문법 오류). 실행 순서는 Actions 워크플로 YAML에 명시된다.

**이 구조를 택한 이유:** 이 시스템의 품질은 선별·요약 프롬프트를 수십 번 고치는 데서 나온다. 단일 스크립트라면 프롬프트 한 번 수정에 "크롤링 수십 건 + LLM 2종 호출" 전체 재실행이 걸리고, 매 실행마다 RSS 내용이 달라져서 프롬프트 변경 효과만 분리해 비교할 수 없다. 단계별 구조에서는 `summarize.py`만 재실행하면 되고, 입력이 고정된 파일이라 비교가 깨끗하다.

부수 효과로 디버깅이 "파일 열어보기"로 끝나고, 전송만 실패했을 때 재실행 비용이 0이며, 파일당 100~150줄이라 읽기 쉽다.

**단계 간 데이터 계약:** JSON이 암묵적 인터페이스가 되는 것을 막기 위해 `pipeline/models.py`에 `dataclass`로 정의해 공유한다.

```python
@dataclass(frozen=True)
class RawItem:          # collect 출력
    source: str
    title: str
    url: str
    published: str      # UTC ISO 8601
    excerpt: str

@dataclass(frozen=True)
class RankedItem:       # rank 출력
    item: RawItem
    score: int          # 0~100
    reason: str         # LLM이 쓴 판단 근거
    topic: str

@dataclass(frozen=True)
class Article:          # enrich 출력
    ranked: RankedItem
    body: str
    body_source: str    # "trafilatura" | "rss_excerpt"

@dataclass(frozen=True)
class Summary:          # summarize 출력
    article: Article
    headline: str       # 30자 이내 (카톡 200자 제약 때문)
    bullets: list[str]  # 2~3개
    why_it_matters: str
```

`RankedItem.reason`은 의도적으로 넣었다. "왜 이 글이 빠졌지"를 파일 열어서 답하는 것이 이 구조의 핵심 이득이고, 그것은 LLM이 근거를 남겨야 성립한다.

**전체 실행 진입점(`run.py`)은 만들지 않는다.** GitHub Actions 워크플로에 6개 step으로 나열하면 Actions UI에서 단계별 로그와 실패 지점이 바로 보인다.

### 3.2 실행 환경: 하이브리드

**운영은 GitHub Actions, 개발·수동 재실행은 로컬.**

- Actions의 cron 지연(혼잡 시 5~30분)은 아침 브리핑이라 무해하다. 정각을 피해 `:20`으로 둔다.
- Actions의 데이터센터 IP 봇 차단 위험은 RSS 우선 수집으로 대부분 회피되고, 차단되는 소스만 로컬 폴백으로 처리한다.
- 로컬은 개발 중 즉시 테스트와 수동 재실행에 쓴다.

Cloudflare Workers는 검토 후 제외했다. 무료 플랜 subrequest 50개 제한이 "소스 다수 fetch + LLM 호출"과 바로 충돌하고, RSS 파싱·본문 추출 라이브러리의 Node 호환성 문제로 작업량이 늘어난다.

**양쪽에서 같은 코드가 돌게 하는 두 개의 추상화:**

1. **`lib/secrets.py`** — 비밀값 통로를 하나로. `python-dotenv`로 로컬 `.env`를 읽고, Actions에서는 Secrets가 이미 환경변수로 주입되므로 `.env`가 없어도 통과한다. 없는 키는 즉시 `RuntimeError`로 죽인다 (파이프라인 중간에 터지는 것보다 낫다).
2. **`lib/store.py`** — 상태 저장소를 하나로. 토큰·본문·좋아요·클릭·실행 이력은 Supabase, 중간 산출물은 로컬 파일.

## 4. 수집

### 4.1 소스 정의 (`config/sources.yaml`)

```yaml
sources:
  - name: 전자신문_오피니언
    url: https://rss.etnews.com/Section902.xml
    kind: rss
    weight: 1.0
    lang: ko

  - name: Hacker_News_Top
    url: https://hnrss.org/best?points=200
    kind: rss
    weight: 1.2
    lang: en
```

`weight`는 LLM 점수에 곱하는 가중치다. "국내 매체 사설"과 "기업 기술블로그"는 나에게 가치가 다르므로 소스 성격을 반영한다. YAML 한 줄 수정으로 튜닝된다.

**실제 소스 목록과 `interests.md` 내용은 구현 1단계에서 확정한다.** 둘 다 품질을 가장 크게 좌우하는 입력이며, 시드 수집(아래)보다 먼저 정해져야 한다.

### 4.2 수집 윈도우: 마지막 발송 이후

```python
window_start = last_sent_at        # state의 마지막 발송 시각
window_start = max(window_start, now - timedelta(hours=96))   # 상한
```

고정 24시간이 아니라 "마지막으로 보낸 그 순간부터 지금까지"로 계산한다. 이 규칙 하나가 요일·공휴일·장애를 모두 처리한다.

| 상황 | 자동으로 나오는 윈도우 |
|---|---|
| 평일 | 약 24시간 |
| 월요일 (주말 쉬고) | 약 72시간 — 주말 해외 콘텐츠가 월요일 브리핑의 공백을 메운다 |
| 연휴 다음 첫 발송일 | 자동으로 늘어남. 공휴일 목록 불필요 |
| 장애로 며칠 멈춘 뒤 복구 | 그 기간을 자동 커버 |
| 같은 날 수동 재실행 | 중복 없이 그 사이 발행분만 |

**96시간 상한**을 두는 이유: 장애로 2주 멈췄다가 복구되면 수집량이 폭증해 크레딧을 한 번에 소진할 수 있다.

**발송 요일은 월~금.** 토·일은 수집도 발송도 하지 않는다. 국내 매체와 기업 기술블로그는 주말 발행이 거의 없고, 주말에 활발한 해외 콘텐츠는 월요일 윈도우에 자연히 포함된다.

### 4.3 수집 깊이: 2단계

전체 수집분은 RSS 제목·발췌만으로 선별하고, 선별을 통과한 상위 10건만 본문을 가져온다.

- 모든 건을 크롤링하면 품질 상한은 올라가지만 외부 서버에 수십~수백 번 요청해 차단·타임아웃이 상시화되고 토큰 비용이 10배 든다.
- RSS 발췌만 쓰면 절대 깨지지 않지만 요약이 제목 보강 수준에 그친다.

### 4.4 중복 제거

- **URL 중복:** 정규화(쿼리스트링·`utm_*` 제거) 후 Supabase의 발행 이력과 비교. 영구 적용.
- **같은 사건 중복:** 최근 14일간 발행한 글의 제목 목록을 `rank` 프롬프트에 함께 넣고 LLM이 판단한다. 14일 x 최대 7건 = 약 100개 제목으로 토큰 부담이 작다.

### 4.5 장애 격리

소스별로 `try/except`로 감싼다. 소스 하나가 실패하면 `raw.json`의 `errors` 배열에 기록하고 계속 진행한다. **전체 소스가 실패하면 중단**한다.

## 5. 선별과 요약

### 5.1 모델

**선별·요약 모두 `claude-opus-5-5`.**

Max 플랜에 월 $100 API 크레딧이 포함되고(claude.ai → Settings → Billing에서 Console 조직 연결 필요, 가입 7일 후 자격 발생, 매 결제 주기 리셋·이월 없음, Claude Code는 비적용), 본 시스템의 예상 사용량은 월 약 $10로 크레딧의 10% 수준이다. 따라서 비용이 모델 선택의 제약이 아니며 품질 기준으로만 고른다.

`lib/llm.py`에서 모델 문자열 한 줄로 교체 가능하게 둔다.

**전송 계층 재시도는 SDK에 맡긴다.** anthropic SDK는 429·5xx·연결 오류를 자체적으로 지수 백오프 재시도한다(`max_retries`). 그 위에 자체 재시도를 겹치면 한 번의 논리적 호출이 여러 배로 늘어나 크레딧을 그만큼 쓴다. `lib/llm.py`는 **예외 분류와 "구조화된 출력 스키마 실패 1회 재시도"만** 담당한다.

**Python 버전: 3.12.** 취향이 아니라 제약이다 — anthropic SDK(검증 시점 2.7.0)가 3.10 이상을 요구하고, 개발 머신의 시스템 `python3`인 3.9는 2025-10-31에 수명이 끝났다. Python에는 LTS가 없고 각 버전이 총 5년을 받는다([PEP 602](https://peps.python.org/pep-0602/)).

### 5.2 선별 (`rank.py`)

`interests.md` 전문과 수집분의 제목·발췌를 **한 번의 호출로** 채점한다. 건당 호출하지 않는 이유는 한 번에 넣어야 LLM이 "이 둘은 같은 사건이니 하나만" 같은 교차 판단을 할 수 있기 때문이다.

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    output_config={
        "effort": "low",     # 채점에는 깊은 추론이 불필요
        "format": {...},     # 각 항목: {index, score, reason, topic}
    },
    messages=[{"role": "user", "content": ranking_prompt}],
)
```

구조화된 출력(`output_config.format`)으로 JSON 스키마를 API 레벨에서 강제한다. 프롬프트로 "JSON으로 답해줘"라고 쓰는 것보다 안정적이다.

출력: 점수 내림차순 상위 10건과 **전체 항목의 점수·이유**를 함께 저장한다. 탈락 이유를 나중에 조회하려면 필요하다.

### 5.3 본문 확보 (`enrich.py`)

`trafilatura`로 광고·내비게이션·푸터를 걷어내고 본문만 추출한다.

- 10건만 요청. 요청 사이 1~2초 간격, 소스별 `robots.txt` 확인.
- 추출 실패 시 **RSS 발췌로 폴백**하고 `body_source`에 기록한다. **이 단계는 절대 중단하지 않는다.**
- 본문은 8,000자에서 자른다. 그 이상은 요약 품질에 기여하지 않으면서 토큰만 소비한다.

### 5.4 요약과 최종 선정 (`summarize.py`)

본문 10건을 읽고 최종 선정 및 요약을 한다. `rank`에서 이미 좁혔는데 또 거르는 이유는, **제목만으로는 알 수 없는 "본문을 읽어보니 내용이 없음"을 여기서 걸러내기 위해서다.** 보도자료 재가공 기사가 대표적이다.

**건수는 점수 임계값으로 결정하고 상한만 7건이다.** 좋은 글이 2건이면 2건만 보낸다.

고정 건수를 쓰지 않는 이유: LLM에게 7건을 채우라고 하면 기준을 낮춰서 채운다. 그것이 며칠 반복되면 "이 브리핑은 별 내용이 없다"가 되고 그 시점에 시스템은 사용되지 않는다. 건수를 채우는 것은 큐레이션을 망치는 가장 흔한 방식이다. 반대로 건수가 적은 것 자체가 "이번 주는 조용했다"는 품질 신호로 작동한다.

**임계값 통과분이 0건인 날에도 한 줄짜리 알림을 보낸다.** 보내지 않으면 "시스템이 죽은 것"과 "오늘 볼 만한 것이 없는 것"이 구분되지 않는다. **0건이어도 `runs`에 발송 이력을 남긴다** — 남기지 않으면 다음 날 윈도우가 계속 늘어나 같은 항목을 반복 평가하게 된다.

- 해외 글은 한국어로 요약한다 (프롬프트에 명시).
- 출력: `headline`(30자 이내), `bullets`(2~3개), `why_it_matters`(한 줄).
- `effort: "medium"`.

**프롬프트 캐싱은 쓰지 않는다.** 캐시 유효시간이 기본 5분이라 하루 1회 실행에는 효과가 없다. (프롬프트 튜닝 중 연달아 실행할 때만 적중하므로 운영 이득이 0이다.)

### 5.5 초기 튜닝 도구

`interests.md`를 처음부터 잘 쓸 수는 없고, 매일 결과를 보며 고치면 튜닝 한 사이클이 하루다. 두 개의 도구로 이를 단축한다.

**`seed.py` (1회성, 소스 확정 직후 실행):** 윈도우 제한을 풀고 각 소스가 제공하는 전체 항목을 긁어 저장한다. **대부분의 RSS 피드는 최근 10~50건만 제공하므로, 지금 수집하지 않으면 영구히 얻을 수 없는 데이터다.** 되돌릴 수 없는 작업이므로 우선순위가 높다.

**`evaluate.py` (운영 비포함):** 여러 날 데이터를 합쳐 선별을 돌리고 점수·이유를 표로 출력한다. 하루치로만 튜닝하면 그 하루에 과적합된다.

## 6. 출력

### 6.1 카카오톡

**API:** `POST https://kapi.kakao.com/v2/api/talk/memo/default/send` (나에게 기본 템플릿으로 메시지 발송)
**인증:** 액세스 토큰, `Content-Type: application/x-www-form-urlencoded;charset=utf-8`
**필수 사전 설정:** 카카오 로그인 활성화, 리다이렉트 URI 등록, **동의항목 `talk_message` ON** (누락 시 403)
**쿼터:** "나에게 보내기"에는 일간·월간 제공량 제한이 없다 (제한은 "친구에게 발송"에만 적용). 토큰 발급 제한은 액세스 토큰 10분당 20개로 하루 1회 실행과 무관하다.

**문서로 확인한 템플릿 제약:**

| 템플릿 | 제약 |
|---|---|
| 텍스트 | `text` **최대 200자**, `link` 필수, 버튼 최대 2개 |
| 리스트 | `header_title` 200자, `contents` **최소 2개 / 최대 3개** |
| 피드 | `title`+`description` 합쳐 최대 4줄 표시 |

기본 템플릿은 마크다운을 지원하지 않는다(plain text).

**따라서 최대 7건을 카톡 한 메시지에 담을 수 없다.** 계산하면 머리글 약 20자 + 건당 약 33자(번호 3자 + 헤드라인 30자)이므로 **5건이 상한**이다(20 + 5x33 = 185자). 7건이면 251자로 초과한다.

**카톡에는 점수 상위 5건만 싣고, 초과분은 "외 N건" 한 줄로 표기한다.** 전체는 웹페이지에 있다. 텍스트 템플릿으로 헤드라인 목록 + 버튼 방식을 쓴다.

```
📡 11/10 IT 브리핑 · 5건

1. (헤드라인)
2. (헤드라인)
3. (헤드라인)
4. (헤드라인)
5. (헤드라인)
   외 2건

[전체 보기]  ← 버튼이 페이지로
```

이 제약에서 `Summary.headline`의 "30자 이내" 요구가 파생된다. 프롬프트에 글자수를 명시하고 **코드에서 검증**한다. 조립 결과가 200자를 넘으면 뒤쪽 건을 "외 N건"으로 접어 반드시 제약 안에 맞춘다.

### 6.2 슬랙 — 운영 경고 전용

**브리핑 전문을 슬랙으로 보내지 않는다.** 전문을 읽는 자리는 웹페이지이고, 슬랙이 그 일을 중복하면 포맷터를 하나 더 유지해야 한다. 혼자 쓰는 시스템에서 읽기 채널이 둘일 이유가 없다.

**그럼에도 슬랙이 필요한 이유는 하나다 — 카카오 토큰이 만료되면 카톡으로는 그 사실을 알릴 수 없다.** 카톡이 유일한 채널이면 시스템이 조용히 죽는다. 슬랙 Incoming Webhook URL은 만료가 없으므로 경고 채널로 가장 안정적이다.

GitHub Actions 실패 메일로 대체되지 않는다. 메일은 *크래시*만 잡는다. "소스 하나가 3일째 0건", "7건 중 5건이 발췌 폴백", "크레딧 70% 소진"은 **실행이 성공적으로 끝나므로** 메일이 오지 않는다. 그런데 이것이 시스템을 서서히 망치는 종류의 실패다(8.4).

슬랙으로 가는 것은 세 가지다.

1. `collect_warnings`의 결과 — 발췌 폴백, 고쳐야 할 소스, 주소가 이전된 소스
2. `lib/guard.py`의 경고 — 토큰 만료 임박, 소스 침묵, 크레딧 조기 소진
3. 단계 실패 리포트 — 어느 단계에서 왜 죽었는지

### 6.2.1 전송 대상의 추상화

보낼 곳이 둘 이상인 것이 확정이므로 `Sender` 프로토콜을 둔다.

```
Sender 프로토콜 (name, send(briefing, raw))
├─ ConsoleSender  — 터미널 출력 (계획 1)
├─ KakaoSender    — 텍스트 템플릿 200자, 상위 5건 + 페이지 버튼 (계획 3)
└─ SlackSender    — 경고 전용 (계획 3)
```

`Protocol`이므로 상속이 없다. 공통 기반 클래스를 통해 엉키지 않으므로 **카톡의 200자 제약이 슬랙 코드에 영향을 주는 일이 구조적으로 불가능하다.** 텔레그램을 추가할 때도 파일 하나만 더하면 된다.

센더는 서로 독립적으로 실패한다. 하나라도 성공하면 실행 이력을 남기고, 전부 실패하면 남기지 않는다 — 남기면 원인을 고친 뒤 재실행이 "이미 보냄"으로 막힌다.

### 6.3 토큰 갱신 (`lib/kakao.py`)

**최초 1회 수동:** 브라우저에서 인가 코드를 받아 `refresh_token`을 발급하고 Supabase에 저장한다. 리다이렉트 URI는 localhost로 등록한다 (최초 인증은 로컬에서만 수행).

**매일 자동:**
```
1. Supabase에서 refresh_token 읽기 (실패 시 로컬 캐시 폴백)
2. POST https://kauth.kakao.com/oauth/token
   grant_type=refresh_token, client_id, refresh_token, client_secret
3. 받은 access_token으로 메시지 전송
4. 응답에 refresh_token이 있으면 저장소 갱신
```

**리프레시 토큰의 수명은 하드코딩하지 않는다.** 카카오 문서는 기간을 숫자로 명시하지 않고 응답의 `refresh_token_expires_in`으로 내려주므로, 그 값을 저장해서 쓴다.

**새 `refresh_token`은 기존 토큰의 만료가 1개월 미만일 때만 응답에 포함된다.** 따라서 매일 실행해도 저장소 쓰기는 한 달에 한 번뿐이다.

### 6.4 웹페이지

**구조: 한 번 빌드한 SPA + JSON 런타임 불러오기.**

React 앱은 코드가 바뀔 때만 빌드한다. 파이프라인은 `docs/data/YYYY-MM-DD.json`만 떨어뜨리고, 앱이 경로의 날짜를 보고 해당 JSON을 불러온다.

매일 전체 빌드 방식을 택하지 않은 **결정적 이유는 파이프라인과 프론트엔드의 분리**다. 매일 빌드하면 "오늘 브리핑을 보내는 일"이 "React 빌드가 성공하는 일"에 묶여서, `package.json` 의존성 하나가 깨지면 카톡이 오지 않는다. 분리하면 프론트엔드가 망가져도 전송은 되고 데이터는 쌓인다. 부수 효과로 아카이브가 1000일이 되어도 배포 비용이 불변이고, 과거 페이지를 매일 재생성하지 않는다.

첫 화면에 짧은 불러오기가 생기지만 브리핑 JSON은 수 KB로 체감되지 않는다. 검색 노출이 약해지는 것은 개인 브리핑이므로 오히려 바람직하다.

**GitHub Pages의 SPA 라우팅:** `/2026-11-10`을 직접 열면 404가 되므로 `404.html` 폴백 처리가 필요하다.

**스택:**

| 항목 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Vite + React + TypeScript | 정적 빌드 결과가 HTML/JS라 Pages에 바로 올라간다. Next.js의 SSR·라우팅은 여기서 쓰이지 않는다 |
| 스타일 | Tailwind CSS | 반응형을 클래스(`md:`, `lg:`)로 처리. 별도 CSS 파일 관리 불필요 |
| 데이터 | 런타임 JSON 불러오기 | 파이프라인에서 Node 의존성 제거 |
| 좋아요·클릭 | Supabase JS 클라이언트 | 브라우저에서 직접. anon key + RLS |

**반응형:** 모바일 1열 카드, 태블릿 이상 2열(`md:grid-cols-2`). 카톡 링크를 통한 모바일 유입이 주 경로이므로 모바일을 기준으로 설계하고 데스크톱으로 확장한다.

**라우팅:** `/`는 최신 브리핑, `/:date`는 해당 날짜. 카톡에 나간 링크가 나중에도 유효해야 하므로 날짜별 영구 링크가 필요하다.

## 7. 데이터

### 7.1 Supabase 테이블 (Phase 1)

```sql
articles        -- 발행된 글의 요약과 메타 (공개 가능한 것만)
article_bodies  -- 기사 본문 전문 + body_source + fallback_reason
                --   별도 테이블로 분리해 anon 권한을 아예 주지 않는다
reactions       -- 좋아요. article_id, created_at
clicks          -- 클릭. article_id, created_at
notes           -- 짧은 메모 + 태그. article_id, text, tags
kakao_auth      -- refresh_token, refresh_token_expires_at, updated_at
runs            -- 실행 이력
                --   window_start, window_end, sent_at(NULL 가능)
                --   status           sent | failed
                --   collected_count  중복 제거 후 수집 건수
                --   considered_count 요약 후보로 올린 건수
                --   max_score        그 실행의 최고 점수 (0건이면 NULL)
                --   published_count  임계값 통과 건수
                --   source_counts    소스별 건수 (jsonb)
                --   input_tokens, errors(jsonb)
                --   errors의 각 항목: {source, kind, message}
                --     kind = config | transient | moved (8.1 참조)
```

**`runs.status`가 있는 이유:** 8.2가 "전송 성공 후에만 이력을 남긴다"로 고정돼 있는데, 그러면 전송이 실패한 날의 `source_counts`가 사라진다. 그것은 8.4의 소스 침묵 경고의 **유일한 입력**이므로, 실패한 날이 빠지면 경고가 그만큼 늦어진다. → 실패한 실행도 `status='failed'`로 남기고, 멱등성 판정과 윈도우 계산은 `status='sent'`만 본다.

**`collected_count`·`considered_count`·`max_score`가 있는 이유:** 0건인 날 페이지가 "후보 10건 / 최고 54점 / 기준 60점"을 보여준다. 0건인 날은 `articles`가 비어 있으므로 **다른 어디에서도 알 수 없다.** 이 숫자가 없으면 "기준이 6점 높았나, 소스가 문제인가"를 판단할 수 없다 — 그 화면의 존재 이유가 이 숫자다.

**Phase 3에서 추가될 것:** `article_chunks (article_id, chunk_index, chunk_text, embedding)`. 본문을 청크로 쪼개 임베딩하면 벡터가 여러 개 생기므로 `article_bodies`에 컬럼으로 넣는 방식(1:1)은 불가능하다. 자세한 근거는 ERD 문서 3.4에 있다.

`runs`는 세 곳에서 쓰인다. **4.2의 윈도우 계산**(`last_sent_at` = 마지막 `sent_at`), **8.2의 멱등성 판정**, **8.3의 소스 침묵 감지**(`source_counts`를 최근 3회분 조회). 별도 테이블 없이 이 하나로 처리한다.

### 7.2 접근 제어

**페이지는 공개 URL로 두고, 노출되면 안 되는 것을 DB에서 막는다.**

| 공개해도 되는 것 | 공개되면 안 되는 것 |
|---|---|
| 내가 쓴 요약·헤드라인·원문 링크 (인용 범위) | **추출한 본문 전문** — 공개 시 타인의 기사를 재배포하는 사이트가 된다 |

- `articles.body`는 RLS로 브라우저 anon key에서 **읽기 불가**로 설정한다.
- `kakao_auth`는 anon key에서 접근 불가.
- `reactions`·`clicks`는 anon key로 **삽입만** 가능.
- 파이프라인은 `SUPABASE_SERVICE_KEY`(쓰기), 브라우저는 `VITE_SUPABASE_ANON_KEY`를 쓴다. 키를 분리하는 것이 RLS가 실제로 작동하는 전제다.
- **`robots.txt` + `noindex` 메타 태그로 검색 색인을 차단한다.** GitHub Pages는 검색엔진에 색인되므로, 이것이 없으면 "아무도 모르는 URL"이라는 전제가 깨진다.

**리포지토리는 퍼블릭이다.** GitHub Pages는 무료 플랜에서 퍼블릭 리포만 지원하고, 이 설계는 비밀값을 리포에 두지 않으므로(전부 Actions Secrets와 Supabase) 퍼블릭이 안전하다. 단 한 가지 규칙이 따라붙는다 — **`articles.body`는 Supabase에만 존재하고 리포에 커밋되지 않는다.** `docs/data/*.json`에는 요약·헤드라인·링크만 담고 본문은 넣지 않는다. 이것이 7.2의 본문 비공개 원칙이 퍼블릭 리포에서도 성립하는 조건이다.

좋아요에 추가 인증(비밀 키, 익명 인증)을 두지 않는다. 위협 모델상 이 URL이 노출될 경로는 내가 공유하는 경우뿐이고, 신호 오염이 생기면 Phase 2에서 바로 드러나 그때 대응할 수 있다. 반면 본문 차단과 색인 차단은 되돌리기 어려우므로 그쪽에 노력을 쓴다.

### 7.3 품질 지표: 좋아요 + 클릭

좋아요만 모으면 "안 누른 나머지"의 의미를 알 수 없다. 싫어서 안 누른 것인지 아예 보지 않은 것인지 구분되지 않아 Phase 2의 학습 신호가 약해진다.

**클릭을 함께 기록해 3단 신호를 만든다.**

| 신호 | 해석 |
|---|---|
| 좋아요 | 강한 긍정 |
| 클릭했으나 좋아요 없음 | 약한 부정 — "열어봤는데 별로" |
| 클릭조차 안 함 | 무관심 |

이는 헤드라인 품질과 선별 품질을 분리해서 평가할 수 있게 한다 ("제목은 끌렸는데 내용이 별로"가 보인다).

명시적 "싫어요" 버튼은 넣지 않는다. 이론적으로는 가장 선명한 신호지만, 혼자 쓰는 도구에서 매일 부정 평가를 입력하는 습관은 유지되지 않는다. 반면 클릭은 원래 하던 행동이라 수집에 추가 노력이 0이고 누락이 없다. 신호 하나의 질이 낮아도 빠짐없이 쌓이는 쪽이 두 달 뒤에 더 많은 정보를 준다. Phase 2에서 클릭 신호만으로 부족하다고 판단되면 그때 버튼을 추가한다.

클릭 기록은 `navigator.sendBeacon`으로 전송해 페이지 이탈 시 유실을 줄인다.

### 7.4 시각 처리 규칙

조용히 틀리기 가장 쉬운 지점이므로 규칙을 명시한다.

- **저장은 모두 UTC ISO 8601.** RSS의 `published`는 매체마다 타임존 표기가 다르므로 수집 시점에 UTC로 정규화한다.
- **윈도우 계산과 화면 표시는 KST.**
- GitHub Actions는 UTC로 동작한다. UTC 22:20 + 9시간 = **익일** 07:20 KST이므로, **KST 월~금은 UTC 일~목**에 해당한다. 따라서 cron은 `20 22 * * 0-4`다. 한 칸 밀리면 토요일에 발송되고 월요일이 빠지므로, 구현 시 실제 발송 요일을 반드시 검증한다.

### 7.5 데이터 보존

- `data/` 중간 산출물: `.gitignore` 처리. **90일 경과분 삭제.**
- `docs/data/*.json`: 영구 보관 (커밋). 건당 수 KB.
- Supabase: 본문 포함 연 약 30MB. 무료 티어 500MB 안. **무료 프로젝트는 1주일 비활성 시 일시정지되지만 매일 쓰므로 해당하지 않는다.**

## 8. 에러 처리와 운영

### 8.1 에러 분류 — Transient와 Permanent

실패를 한 덩어리로 다루면 서로 다른 문제가 같은 기록이 된다. 피드가 404(주소가 죽음)인 것과 503(일시 장애)인 것이 같은 문자열로 남으면, 전자는 `sources.yaml`을 고쳐야 하고 후자는 기다리면 되는데 로그만 보고는 구분할 수 없다.

그래서 **"호출자가 무엇을 해야 하는가"**를 유일한 기준으로 두 갈래만 만든다. 상태 코드만큼 갈래를 늘리면 호출부마다 분기가 생기고 결국 아무도 유지하지 않는다.

| 갈래 | 뜻 | 해당 상황 |
|---|---|---|
| **Transient** | 기다리면 된다. 지수 백오프로 재시도하고, `Retry-After` 헤더가 있으면 그 값을 따른다 | 408, 425, 429, 5xx(501·505 제외), 타임아웃, 연결 실패 |
| **Permanent** | 설정을 고쳐야 한다. **재시도하지 않는다** | 400, 401, **403**, 404, 410, 451, 501, 505, 주소 오타, 리다이렉트 루프 |

판단이 갈리는 지점을 명시한다.

- **403은 Permanent다.** 봇 차단이므로 재시도해도 결과가 같다. 본문 확보 단계에서 10건에 재시도를 걸면 수십 초를 버린다.
- **501·505는 Permanent다.** 5xx지만 "서버가 그 기능을 지원하지 않음"이므로 기다려도 생기지 않는다.
- **301·308은 실패가 아니다.** 자동으로 따라가되 원래 주소를 기록해 `sources.yaml` 갱신을 알린다. 302·303·307은 임시 이전이므로 기록하지 않는다.
- **분류되지 않은 예외는 삼키지 않는다.** `TypeError` 같은 코드 버그를 Transient로 감싸면 재시도로 가려져 원인을 찾을 수 없다.

분류 규칙은 `lib/http.py` 한곳에 둔다. 두 곳에 두면 "403을 어디선 재시도하고 어디선 안 하는" 상태가 된다.

수집 실패는 이 분류를 `SourceError.kind`로 기록한다 — `config`(고쳐야 함) / `transient`(기다리면 됨) / `moved`(이전됨). 8.4의 소스 침묵 경고가 **"죽은 소스"와 "불안정한 소스"를 구분**하는 근거가 된다.

**비밀값은 에러 메시지에 넣지 않는다.** 슬랙 웹훅 URL이 대표적이다 — 에러 메시지는 슬랙, 로그, Actions 출력에 그대로 남는다.

### 8.2 단계별 실패 정책

원칙: **일부가 깨져도 오늘 브리핑은 나간다.** 완벽한 브리핑보다 오는 브리핑이 낫다.

| 단계 | Permanent일 때 | Transient일 때 | 이유 |
|---|---|---|---|
| `collect` | 재시도 없이 `kind=config`로 기록하고 계속 | 2회 시도 후 `kind=transient`로 기록하고 계속 | 매체 하나의 장애로 그날이 날아가면 안 된다. 전부 실패하면 중단하는데, **전부 config면 안내가 "네트워크 확인"이 아니라 "sources.yaml 확인"이 된다** |
| `rank` | 중단 | SDK가 재시도, 스키마 실패만 1회 추가 재시도 | 점수가 없으면 선별이 불가능하고 폴백할 것이 없다 |
| `enrich` | **즉시** RSS 발췌로 폴백 | 2회 시도 후 발췌로 폴백 | 외부 크롤링은 가장 자주 깨지면서 유일하게 폴백이 있는 단계다. **절대 중단하지 않는다.** 폴백 이유를 `Article.fallback_reason`에 남긴다 |
| `summarize` | 중단 | SDK가 재시도, 스키마 실패만 1회 추가 재시도 | 요약이 결과물 자체다 |
| `render` | 중단 | 중단 | JSON이 없으면 카톡 버튼이 죽은 링크가 된다 |
| `notify` | **즉시** 실패 (웹훅·토큰을 고쳐야 한다) | 3회 시도 | 카톡과 슬랙은 독립 처리한다 — 카톡 토큰 만료로 슬랙까지 못 받는 것은 불합리하다 |

전송이 실패하면 **실행 이력을 남기지 않는다.** 먼저 남기면 전송 실패 후 재실행이 "이미 보냄"으로 막혀 그날 브리핑이 사라진다.

### 8.3 멱등성

`notify.py`는 저장된 발송 이력을 확인한다. 같은 윈도우에 대해 이미 보냈으면 건너뛰고, `--force` 플래그로만 우회한다. Actions cron 중복 실행이나 수동 재실행 시 카톡이 두 번 가는 것을 막는다.

판정은 **`status='sent'`인 행만** 본다. 실패한 실행도 기록에 남지만(7.1), 그것을 "보냈다"로 세면 원인을 고친 뒤 재실행이 막히고 그날 브리핑이 사라진다. DB 쪽에도 제약을 걸어 `status`와 `sent_at`이 어긋나는 행이 들어오지 못하게 한다 — 둘이 어긋나면 윈도우 계산이 조용히 틀어진다.

명령행 인자는 `argparse`로 처리한다.

**어제 분을 나중에 복구하는 것은 불가능하다.** RSS는 과거 항목을 충분히 제공하지 않으므로, 하루를 놓치면 그 하루는 회복되지 않는다. 이를 받아들인다.

### 8.4 경고 장치 (`lib/guard.py`)

조용히 실패하는 것이 최악이다. 브리핑이 오지 않으면 "오늘 뉴스가 없었나보다"로 착각하게 되고, 그것이 2주 지속되면 시스템이 죽은 것을 모른다.

| 대상 | 임계값 | 동작 |
|---|---|---|
| **소스 침묵** | 3일 연속 0건 | 슬랙 경고. 주말 때문에 하루 0건은 흔하므로 느슨하게 둔다. `runs.status`가 있어 **전송이 실패한 날의 수집 기록도 포함**되므로 카운트가 정확하다 |
| **토큰 만료** | 만료 14일 전부터 | 슬랙 경고 + 재인증 방법 안내 |
| **크레딧 소진** | 월 크레딧의 일정 비율 초과 또는 입력 토큰이 평소의 3배 초과 | 중단하고 경고 |

세 항목의 가치 순서는 **소스 침묵 > 토큰 만료 > 크레딧**이다. 토큰 만료는 치명적이지만 한 번 겪으면 알게 되고 복구된다. 소스 침묵은 겪어도 알 수 없다 — 브리핑은 정상적으로 오고 내용만 조금씩 빈약해진다. 그것이 반년 누적되면 시스템을 쓸 이유가 없어지는데 그 과정에 아무 신호가 없다. 가장 위험한 종류의 실패다.

**임계값을 모두 느슨하게 둔 이유:** 여기서 진짜 비용은 코드가 아니라 알림 피로다. 오탐이 세 번 나면 경고를 무시하게 되고, 그러면 경고 시스템이 있는 것이 없는 것보다 나쁘다.

**크레딧 가드의 의미:** 요금 폭주 방지가 아니라 조기 소진 방지다. Max 크레딧은 이월되지 않고, 월 중반에 바닥나면 그 달의 나머지 기간 동안 API 요청이 중단되어 브리핑이 오지 않는다.

### 8.5 실패 알림

1. GitHub Actions 실패 시 자동 메일 (기본 제공)
2. 슬랙에 실패 리포트 — 어느 단계에서 왜 죽었는지. 슬랙은 토큰 만료가 없어 알림 채널로 가장 안정적이다(6.2). **메일은 크래시만 잡고, 성공적으로 끝나는 품질 저하는 못 잡는다**
3. 부분 실패도 리포트 — "7건 중 2건은 RSS 발췌로 폴백" 같은 경고를 브리핑 하단에 작게 표시

### 8.6 GitHub Actions 워크플로

```yaml
on:
  schedule:
    - cron: '20 22 * * 0-4'   # UTC → 월~금 07:20 KST
  workflow_dispatch:

jobs:
  briefing:
    steps:
      - run: python -m pipeline.collect
      - run: python -m pipeline.rank
      - run: python -m pipeline.enrich
      - run: python -m pipeline.summarize
      - run: python -m pipeline.render
      - run: python -m pipeline.notify
      - if: failure()
        run: python -m pipeline.report_failure
      # 마지막: docs/ 커밋·푸시
```

정각(`0 * * * *`)을 피한 이유는 GitHub Actions cron이 정각에 전 세계 작업이 몰려 지연이 가장 크기 때문이다.

Node 셋업 step은 불필요하다 (6.4의 SPA 분리 결정 덕분).

### 8.7 비밀값

로컬은 `.env`, Actions는 Secrets에 같은 이름으로 둔다.

```
ANTHROPIC_API_KEY          # Max 크레딧이 연결된 Console 조직의 키
KAKAO_REST_API_KEY
KAKAO_CLIENT_SECRET
SLACK_WEBHOOK_URL
SUPABASE_URL
SUPABASE_SERVICE_KEY       # 파이프라인용 (쓰기)
VITE_SUPABASE_ANON_KEY     # 브라우저용 (RLS로 보호)
```

**Max 크레딧은 플랜 1개 ↔ Console 조직 1개로 연결되고 본인이 변경할 수 없다(변경은 지원팀 문의).** 따라서 `ANTHROPIC_API_KEY`는 크레딧이 연결된 조직에서 발급해야 한다.

## 9. 테스트

**테스트하지 않을 것을 먼저 정한다.**

**LLM 출력 품질은 테스트하지 않는다.** "요약이 좋은가"는 단위 테스트로 검증 불가능하고, 시도하면 깨지기만 하는 테스트가 된다. 품질은 `interests.md`와 프롬프트를 고치면서 `evaluate.py`로 비교하는 영역이다.

**테스트할 것:**

```python
def test_카톡_메시지가_200자를_넘지_않는다()
def test_헤드라인이_30자_제약을_지킨다()
def test_소스_하나가_죽어도_나머지는_수집된다()
def test_본문_추출_실패시_RSS_발췌로_폴백한다()
def test_URL_정규화가_utm_파라미터를_제거한다()
def test_임계값_미달이면_건수가_줄어든다()
def test_임계값_통과분이_0건이어도_알림을_보낸다()
def test_마지막_발송_이후로_윈도우가_계산된다()
def test_윈도우가_96시간을_넘지_않는다()
def test_같은_윈도우에_두_번_전송하지_않는다()
def test_published_타임존이_UTC로_정규화된다()
def test_403은_재시도하지_않는다()
def test_429의_Retry_After를_존중한다()
def test_전부_설정_문제면_안내가_sources_yaml을_가리킨다()
def test_에러_메시지에_웹훅_URL이_들어가지_않는다()
def test_분류되지_않은_예외는_삼키지_않는다()
```

`tests/fixtures/`에 실제 RSS XML 샘플을 저장해 네트워크 없이 파싱을 테스트한다. LLM 호출은 **저장된 응답을 재생**해 실제 API를 호출하지 않는다 — 테스트가 빠르고 비용이 없고 결정적이다.

`pytest`를 쓴다.

## 10. 구현 순서

시드 수집이 되돌릴 수 없는 작업이므로 소스·관심사 확정을 앞에 둔다.

1. **환경 세팅** — Python 3.12, git 리포(**퍼블릭**), Supabase 프로젝트, Console 조직 크레딧 연결. 카카오 앱 등록과 슬랙 Webhook은 계획 3에서 한다
2. **기반 모듈** — `lib/urls.py`, `lib/timeutil.py`, `lib/retry.py`, `lib/http.py`, `models.py`, `lib/secrets.py`, `lib/store.py`. 뒤의 모든 단계가 여기에 의존하므로 먼저 세운다
3. **`config/sources.yaml` + `config/interests.md` 확정**
4. **`seed.py` 실행** — 각 소스의 전체 제공분 확보 (지금 하지 않으면 영구 손실)
5. **`rank.py` + `evaluate.py`** — 시드 데이터로 선별 프롬프트 튜닝
6. **`collect.py` / `enrich.py` / `summarize.py`**
7. **`notify.py` + `lib/sender.py`의 `ConsoleSender`** — 여기까지면 로컬에서 브리핑이 터미널에 나오고 발행 이력이 쌓인다. **큐레이션 품질 튜닝을 여기서 끝낸다**
8. **`render.py` + React 앱** (좋아요·클릭 저장 포함)
9. **`KakaoSender`**(토큰 최초 인증 포함) + **`SlackSender`**(경고 전용) — 페이지가 있어야 "전체 보기" 버튼이 성립하므로 8 다음이다
