- 작성일: 2026-11-11
- 대상: `supabase/schema.sql`
- 설계 스펙: `2026-11-10-it-column-automation-design.md` 7장

페이지 목업을 만들면서 **스키마에 없는 데이터를 화면이 요구하는 것**을 발견했다. 이 문서는 관계를 그림으로 확인하고 그 누락을 해소한다.

## 2. 공개 범위 — 이 표가 ERD의 핵심이다

리포지토리가 퍼블릭이고 페이지도 공개 URL이므로, **어떤 테이블이 브라우저에서 읽히는지**가 가장 중요한 속성이다.

| 테이블 | anon 권한 | 이유 |
|---|---|---|
| `articles` | **SELECT** | 공개 페이지가 요약·헤드라인·링크를 읽는다 |
| `reactions` | **INSERT만** | 좋아요를 누른다. 집계 조회는 service_role만 |
| `clicks` | **INSERT만** | 클릭을 기록한다 |
| `notes` | SELECT + INSERT | 내가 쓴 메모를 내 페이지에서 보고 쓴다 |
| `article_bodies` | **없음** | **타인의 기사 전문이다. 공개되면 재배포가 된다** |
| `article_chunks` | **없음** | 본문 조각이므로 `article_bodies`와 같은 정책 |
| `runs` | **없음** | 실행 이력. 에러 메시지에 내부 정보가 담긴다 |
| `kakao_auth` | **없음** | 토큰 |

**`article_bodies`를 `articles`에서 분리한 이유가 여기서 보인다.** 한 테이블이었다면 RLS는 행 단위라 컬럼을 가릴 수 없고, 컬럼 권한을 따로 관리해야 한다. 테이블을 쪼개면 권한이 테이블 단위라 `anon` 키로 조회를 시도해보는 것 한 번으로 검증이 끝난다.

**`article_chunks`도 같은 이유로 `article_bodies`에 컬럼으로 넣지 않는다** — 3.4에서 다시 설명한다.

## 3. 관계 설명

### 3.1 `articles` 1:1 `article_bodies`

`article_bodies.article_id`가 **기본키이면서 외래 키**다. 이것이 1:1을 DB 차원에서 강제한다 — 한 기사에 본문이 두 개 들어갈 수 없다.

`on delete cascade`를 걸어 기사를 지우면 본문도 함께 사라진다. 본문만 남아 떠도는 것을 막는다.

### 3.2 `articles` 1:N `reactions` / `clicks` / `notes`

좋아요는 한 기사에 여러 번 눌릴 수 있다(기기가 다르거나 실수로 두 번). **의도적으로 유일성 제약을 걸지 않는다** — 1인용이므로 중복을 막는 것보다 집계가 간단한 쪽이 낫고, 중복이 생기면 `count(distinct date_trunc('day', created_at))` 같은 식으로 처리하면 된다.

클릭은 당연히 여러 번이다. 메모도 여러 개를 쓸 수 있다.

세 테이블 모두 `article_id`에 인덱스를 만든다. 외래 키 컬럼에 인덱스가 없으면 부모 행 삭제 시 자식 테이블을 전체 스캔하고, `article_id`로 집계할 때도 느리다.

### 3.3 `runs`는 왜 `articles`와 외래 키로 이어지지 않나

`articles.run_id`를 두는 것을 검토했고 **지금은 넣지 않는다.**

넣고 싶은 이유는 "이 실행에서 무엇을 발행했나"가 직접 조회되는 것이다. 그런데 비용이 있다. 설계 8.2가 **"전송에 성공한 뒤에 이력을 남긴다"**로 고정돼 있어서, `articles`를 저장하는 시점에는 `run_id`가 아직 없다. 순서를 바꾸면 "전송 실패 시 이력 없음" 보장이 깨지고, 두 단계로 쓰면 트랜잭션이 필요해진다.

대신 `articles.briefing_date`와 `runs.window_end`로 느슨하게 이어진다. 1인용이고 하루 한 번 실행이므로 이 정도로 충분하다. **같은 날 두 번 발행하는 경우는 `--force`뿐이고, 그때는 `url` 유일 제약이 upsert로 덮어쓴다.**

Phase 2에서 "실행별 적중률"을 정확히 보고 싶어지면 그때 추가한다. 그 시점에는 쓰기 순서를 바꿀 근거도 생긴다.

### 3.4 Phase 3의 임베딩은 왜 별도 테이블인가

**본문 하나를 청크로 쪼개 임베딩하면 벡터가 여러 개 생긴다.** 8,000자 본문을 500자씩 나누면 16개다. 따라서 `article_bodies`에 `embedding` 컬럼을 추가하는 방식은 처음부터 불가능하다 — 그건 1:1 구조다.

`article_chunks (article_id, chunk_index, chunk_text, embedding)`로 1:N을 만든다.

**차원 수는 지금 정하지 않는다.** 쓸 임베딩 모델에 따라 달라지고(모델마다 384~3072), `vector(N)`의 N은 나중에 바꾸면 기존 데이터를 다시 임베딩해야 한다. Phase 3에서 모델을 고른 뒤 확정한다.

**pgvector 인덱스(HNSW 또는 IVFFlat)는 데이터가 쌓인 뒤에 만든다.** 빈 테이블에 만들면 통계가 없어 비효율적인 인덱스가 된다.

이 테이블은 **Phase 1에서 만들지 않는다.** 스키마에 없어도 Phase 1·2가 돌아가고, Phase 3 시작 시 `create table` 한 번으로 추가된다. 지금 만들어두면 빈 테이블이 권한 설정만 차지한다.

## 4. 목업이 찾아낸 누락

페이지를 그려보니 **화면이 요구하는 값이 DB에 없는 것**이 드러났다. 세 개는 쿼리로 해결되고, 세 개는 컬럼이 필요하다.

### 4.1 쿼리로 해결되는 것 — 컬럼 불필요

| 화면 | 필요한 값 | 해결 |
|---|---|---|
| 모든 화면 하단 | "이번 주 · 발행 19 · 좋아요 6 · 클릭 11" | `articles`와 `reactions`/`clicks`를 조인해 집계 |
| 아카이브 목록 | "MCP 스펙 2.0 외 4건" | 그 날짜의 `articles`에서 `score` 최고 1건 + 전체 건수 |
| 아카이브 목록 | 0건인 날 표시 | `runs`에 행은 있고 그 날짜의 `articles`가 없는 경우 |

집계를 컬럼으로 캐싱하지 않는 이유: **하루 한 번 보는 화면이고 데이터가 연 수백 건이다.** 캐싱하면 값이 틀어질 경로만 늘어난다.

### 4.2 컬럼이 필요한 것

**`runs.considered_count`** — 0건인 날 화면의 "후보 10건"이다. 이것은 `Briefing.considered`인데 **지금 DB에 저장되지 않는다.** `source_counts`의 합으로는 계산할 수 없다 — 중복 제거와 발행 이력 필터를 거친 뒤의 수이기 때문이다.

**`runs.max_score`** — 0건인 날 화면의 "최고 점수 54점"이다. **0건인 날은 `articles`가 비어 있어서 어디에서도 알 수 없다.** 이 값이 없으면 "기준이 6점 높았나, 아니면 소스가 문제인가"를 판단할 수 없다. 0건인 날 화면의 존재 이유가 이 숫자다.

**`runs.collected_count`** — 중복 제거 후 수집 건수. `considered_count`와 구분된다(선별 전/후).

### 4.3 추가로 발견한 것 — `runs.status`

ERD를 그리다 보니 **전송이 실패하면 그 실행의 모든 기록이 사라진다**는 것을 알았다. 설계 8.2가 "전송 성공 후에만 이력을 남긴다"이고, 그것은 재실행을 가능하게 하려는 올바른 결정이다. 그런데 부작용이 있다.

`runs.source_counts`는 **8.4의 "소스 3일 연속 0건" 경고의 유일한 입력**이다. 전송이 실패한 날은 그 카운트에서 빠지므로, **경고가 늦어진다.** 토큰이 만료돼 3일간 전송이 실패하는 동안 소스도 죽었다면, 그 소스는 6일 뒤에야 경고된다.

→ `status text not null` (`'sent'` | `'failed'`)를 추가한다.

- 전송 실패 시에도 `status='failed'`로 행을 남긴다
- 멱등성 판정과 윈도우 계산은 `where status = 'sent'`만 본다 → 재실행이 막히지 않는다
- `source_counts`가 실패한 날도 남아 경고가 정확해진다
- `sent_at`은 `'failed'`인 행에서 `NULL`이 된다

**비용은 작다.** `notify`가 실패 경로에서 `record_run(status='failed')`를 한 번 더 호출하고, `last_sent_at` 쿼리에 조건 한 줄이 붙는다.

### 4.4 `article_bodies.fallback_reason`

계획에서 `Article.fallback_reason`을 모델에 추가했는데 **스키마에는 반영하지 않았다.** 추가한다. 이것으로 "이 소스는 늘 403이 난다"를 과거 기록에서 확인할 수 있다.

## 5. 변경 요약

```
runs 에 추가:
  status            text  not null  check (status in ('sent','failed'))
  collected_count   int   not null default 0
  considered_count  int   not null default 0
  max_score         int               -- 수집 0건이면 NULL
  sent_at           timestamptz       -- nullable로 변경 (failed면 NULL)

article_bodies 에 추가:
  fallback_reason   text              -- 폴백이 없으면 NULL

Phase 3에서 추가 (지금은 만들지 않음):
  article_chunks (id, article_id FK, chunk_index, chunk_text, embedding vector(N))
```

인덱스도 하나 바꾼다.

```
runs_sent_at_idx → runs (sent_at desc) where status = 'sent'
```

**부분 인덱스(partial index)**다. `last_sent_at` 조회가 항상 `status='sent'`를 거치므로, 실패한 행을 인덱스에서 빼면 더 작고 빠르다.

| 항목 | 언제 정하나 | 왜 지금 못 정하나 |
